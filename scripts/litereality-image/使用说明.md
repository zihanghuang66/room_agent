# LiteReality-Agent 镜像构建包 v0.1.3

用途：交给学校平台构建 `linux/amd64` 镜像，以后每次申请容器直接选择这个镜像。
这份交付是 **Dockerfile 构建配方**，不是已经构建完成的镜像。本地没有 Docker 引擎，未实际执行镜像构建或 Linux GPU 测试。

## v0.1.3 修复内容

用户回传的 v0.1.2 构建日志已证实：内网基础镜像拉取成功，Ubuntu 22.04.4 / 原始 nvcc 12.5.40；CUDA 12.4 安装、终端配置、LiteReality 基础依赖导入和 CLI 均通过。真正中止点是原 Step 13 下载 Blender 时 `download.blender.org` 返回 HTTP 403，curl 返回 22。之前 uv 安装中的 DNS 重试随后成功，不是本次终止原因。日志不包含 403 响应正文，不能确定是源站规则还是中间代理/网关返回。

改为优先使用公开 FreeDif Blender 镜像，原官方下载地址作为备用。Mac 已完整读取该镜像安装包，396237880 字节，SHA256 与原官方包一致：`aaccb355f50183979b698bcce7467103a76261b5fa59f4972295842662a285fb`。这验证了镜像内容，不代表学校构建节点也一定能连接它。

每次下载使用独立临时文件，HTTP/网络失败可尝试下一配置源；校验成功才进入解压，SHA256 不符立即失败。保留 HTTPS 证书校验并禁止降级到 HTTP，终端输出下载源、HTTP 状态、curl 退出码与校验结果。全部源失败会明确停止，不会跳过 Blender 安装继续假报成功。

为保留构建缓存，前面已通过的 v0.1.2 构建指令和载荷保持不变，下载修复以第二段内嵌载荷在 tools 步骤前应用。早期层的 version 标签仍为 0.1.2，最终镜像标签会更新为 0.1.3；这不是上传错版本。是否实际命中缓存取决于学校是否保留相同构建节点/缓存及基础镜像内容。`base_payload/` 保存原始载荷，`payload/` 保存补丁后的最终源码，两个载荷各自有 SHA256 校验。

v0.1.2 改为用户从学校导出日志提供的精确地址：`10.27.130.24:5000/pytorch/pytorch-admin:24.06-py3`。不再使用先前推测的 `21.10-py3` 地址，也无需先运行独立探测 Dockerfile。日志只能证明平台尝试拉取这个地址，不能据此得出完整镜像目录、拉取已经成功或学校镜像内部未修改。完整构建开头会打印并检查 Ubuntu 22.04/x86_64，保留基础系统和 nvcc 版本记录。

## 学校平台操作

1. 上传单独的 `room-litereality-agent-v0.1.3.Dockerfile`；若平台要求文件名为 `Dockerfile`，重命名后上传，或直接使用压缩包内的 `Dockerfile`。
2. 选择 `linux/amd64` / x86_64。建议镜像名称 `room-litereality-agent:0.1.3`。Dockerfile 没有 `COPY` / `ADD`，**只需上传这一个文件**，不依赖旧容器、本地源码或扫描文件。
3. 使用平台默认构建入口。FROM 仅引用学校内网仓库，不再请求 Docker Hub；平台构建器需有该内网仓库的访问权限。后续安装仍需要 Ubuntu 软件源、NVIDIA CUDA 软件源、GitHub/codeload、PyPI、download.pytorch.org、mirror.freedif.org（Blender 首选）、download.blender.org（备用）、nodejs.org。无法联网时会明确失败，不会关闭证书检查。
4. 构建成功后，启动新容器并分配 GPU；把原持久化项目目录挂载到 `/yinxin/projects/room`，保持现有目录内容。安装好的环境在 `/opt/room`，不会被这个挂载覆盖。
5. 若平台已有 SSH/Web Terminal，保留其入口；普通默认启动命令是 `/opt/room/image/entrypoint.sh sleep infinity`。需要镜像自行运行 SSH 服务时，按下文“SSH 与 tmux”选择启动命令。镜像不会阻止平台按闲置策略回收容器。
6. 平台终端运行：

```bash
/usr/local/bin/room-check
```

无需先解压脚本。脚本会逐项显示状态和关键错误，并生成：

```text
/yinxin/projects/room/return_output/room_image_check_<时间>_<随机值>.tar.gz
```

把返回包发来检查。如果 **构建阶段** 失败，容器尚不存在，`room-check` 无法运行；请导出学校平台的完整构建日志，至少保留第一个失败的 `RUN` 层及其错误上下文。

## 包内启动脚本的完整命令（可选）

单文件导入无需这一步。如果希望上传源码包并使用包内启动脚本，把 tar 放在 `/yinxin/projects/room/scripts/`，然后在新镜像容器中执行：

```bash
mkdir -p /yinxin/projects/room/scripts
tar -xzf /yinxin/projects/room/scripts/room-litereality-image-v0.1.3.tar.gz -C /yinxin/projects/room/scripts
bash /yinxin/projects/room/scripts/room-litereality-image-v0.1.3/run_after_start.sh
```

## 镜像内包含什么

| 组件 | 版本或配置 |
| --- | --- |
| 基础系统 | 学校内网 `pytorch/pytorch-admin:24.06-py3`；实际内部配置待构建检查，未取得镜像摘要 |
| CUDA 编译工具 | 单独安装 `cuda-toolkit-12-4=12.4.1-1`，使用 `/usr/local/cuda-12.4`，仅 Toolkit，不安装驱动 |
| LiteReality | `28ffe1fd4a1b03c93f1877a33a8bc9b806f72fe1`，源码 tar SHA256 校验 |
| Codex 适配 | Room v0.1.2，沿用已修复的事件判断、MCP、文件编辑错误记录 |
| Codex CLI | 0.164.0，官方 Linux musl 二进制及 SHA256 |
| Blender | 5.1.2，官方 Linux x64 包及 SHA256 |
| Node.js | 22.23.4，官方 Linux x64 包及 SHA256 |
| Agent Python 环境 | `/opt/room/envs/app`，Python 3.10，上游 uv.lock 加已验证的 Linux Open3D 兼容补丁 |
| GPU Python 环境 | `/opt/room/envs/gpu`，torch 2.6.0+cu124、torchvision 0.21.0+cu124、transformers 4.57.5、xformers 0.0.29.post3 |
| TRELLIS 原生扩展 | CuMesh、FlexGEMM、O-Voxel、nvdiffrast、nvdiffrec，全部锁定源码提交，构建时编译 |
| 通用图形依赖 | EGL/GLVND/Mesa、图像和视频库；不包含宿主 NVIDIA 驱动 |
| SSH / 终端 | OpenSSH 客户端与服务端、SFTP、tmux、zsh、Ghostty xterm-ghostty terminfo、tmux-256color |
| 常用工具 | rsync、Vim（轻量版）、nano、less、htop、jq、ripgrep、procps、iproute2、ping、DNS 工具、UTF-8 locale |

GroundingDINO、DINOv2 与 TRELLIS 共享独立 GPU 环境，与 Agent 的轻量环境隔离。与上游 DINO 专用镜像使用 torch 2.5.1 不同，这里统一到 TRELLIS 所需的 torch 2.6.0；实际检测推理仍需 GPU 测试。

NVIDIA 原版 24.06 是 Ubuntu 22.04/Python 3.10/CUDA 12.5，学校的 `pytorch-admin` 是定制名称，不能直接当成原版。新配方显式使用 root 构建、隔离 uv 引导环境、清除继承的 Python 包路径/旧 pip 约束及 CUDA 库搜索路径，然后建立自己的 venv；不使用基础镜像自带的 torch 开发版。Codex/Node/Blender 命令放在 `/opt/room/bin` 优先使用，避免与基础镜像已有同名程序发生安装冲突。

为了继续使用已锁定的 torch 2.6/cu124 和原生扩展，补装 CUDA 12.4 Toolkit 并显式选择其编译器/头文件/链接 stub，不把基础镜像自带 CUDA 12.5 编译器混进来。若已有完整 CUDA 12.4 开发文件则复用。此选择会增加镜像体积、下载量和首次构建耗时，但不更换宿主 NVIDIA 驱动。

构建器只需 CPU：直接调用各扩展的编译入口，使用 CUDA Toolkit、显式架构和链接用的 CUDA stub，不调用上游要求 `nvidia-smi` 的安装包装脚本。编译链接路径不进入运行时 `LD_LIBRARY_PATH`。构建结束检查编译产物是否存在；加载驱动、执行 CUDA 内核放在新容器中检查，不能把两者混为一谈。

默认编译架构 `8.0;8.6;8.9+PTX`，面向 A100/3090/4090。默认 `BUILD_JOBS=2` 限制并行编译；若构建被 OOM 杀掉，可以将平台构建参数 `BUILD_JOBS` 改为 `1`。首次编译较重，镜像大小、耗时、峰值内存尚未实测；平台的磁盘配额和构建超时可能影响结果。

源码、主要二进制、Python 依赖已锁定。学校基础镜像目前按提供的标签引用，尚未取得不可变 digest；Ubuntu apt 软件源也未做时间快照，因此不承诺逐字节一致的镜像重建。完整 Python 安装清单和构建环境记录保存在镜像 `/opt/room/build-info/`。

## SSH 与 tmux

SSH 服务端/客户端都已安装。**优先保留学校的 SSH 入口和账号配置**；不覆盖 `/etc/ssh/sshd_config`，也不在默认启动中额外抢占 22 端口。

如果平台要求镜像自行提供 SSH：在平台配置中注入登录用户的公钥（`~/.ssh/authorized_keys`），配置容器端口 22 的映射，并将启动命令设为：

```bash
/opt/room/image/entrypoint.sh /usr/local/bin/room-sshd
```

此入口以 root 启动 sshd，前台运行，使用独立配置 `/opt/room/image/sshd_config`；仅允许公钥认证，不设置默认密码。运行时生成本容器的主机密钥；构建时由 apt 自动生成的主机私钥已在同一层删除。更换容器时主机密钥可能变化，连接地址和主机指纹以学校平台为准。支持通过平台环境变量 `ROOM_SSH_PORT` 修改容器内监听端口。

本说明不虚构学校的 SSH 地址/端口；建立服务不等于平台已经开放外部连接。该入口不自动下载公钥、不读取或打包你的私钥。若学校自己启动 sshd，此独立配置不影响它。

SSH 登录后创建或恢复名为 room 的 tmux 会话：

```bash
/usr/local/bin/room-tmux
```

会话内运行任务；按 `Ctrl-b` 再按 `d` 分离，重新登录后运行同一条命令恢复。tmux 只能抵抗 SSH 断线，**无法让进程跨容器停止、删除或重建继续运行**。

Ghostty 的图形终端在 Mac 上运行；无桌面的学校 GPU 容器内安装其完整 GUI 没有必要。本镜像安装从官方 Ghostty 1.3.1 应用导出的 `xterm-ghostty` terminfo，并用 `tic` 编译到系统目录，解决 SSH 后 unknown terminal、tmux 终端能力不匹配等问题，不强制覆盖 SSH 传来的 `TERM`。tmux 内使用 `tmux-256color` 并声明 Ghostty 的真彩色支持。依据：[Ghostty 官方远端 terminfo 说明](https://ghostty.org/docs/help/terminfo)。

## 模型、扫描和登录

- 扫描保留在 `/yinxin/projects/room/data/raw/`；不会加入镜像。
- 权重保留在 `/yinxin/projects/room/return_output/cache/litereality-models/`；不会在镜像构建时下载。
- 运行工作目录和输出在 `/yinxin/projects/room/return_output/litereality_workspace/`。
- Codex 登录凭据和图像生成 API 密钥不加入 Dockerfile、镜像或回传包。新容器需恢复有效登录；若平台支持额外挂载，可把专用持久化凭据目录挂载至容器用户的 `.codex` 目录。不要把凭据目录作为 Docker 构建上下文。
- Agent provider 全部使用 Codex。锁定环境中仍保留上游 Python 依赖清单里的 Claude SDK 包，但本适配器禁用 Claude 执行和回退。

环境检查后，需要下载模型时，在新容器中执行已内置的脚本：

```bash
/usr/local/bin/room-fetch-models
```

会下载 GroundingDINO、DINOv2、TRELLIS.2-4B 和 DINOv3，具体提交见 `pins.json`。下载量较大，需要持久化盘有足够空间和网络权限；支持 Hugging Face 缓存复用。DINOv3 使用 LiteReality 上游部署脚本指定的 camenduru 镜像、固定提交及权重 SHA256；不是 VGGT-Ω 权重，也不会读取之前的 Omega 模型。脚本保留模型仓库自身的许可文件。

下载后生成本地 TRELLIS pipeline 配置，不修改原始权重。DINO 和 TRELLIS 运行入口指向固定的本地模型路径，不自动换成模型仓库的最新 main。下载成功仅代表权重准备完毕，尚不等于模型推理成功。

查看应用 CLI：

```bash
/usr/local/bin/room-litereality --help
```

## 验收范围与现存缺口

`room-check` 不调用付费模型、不下载权重、不重建真实房间。检查内容包括：Agent 依赖、CLI、CUDA 张量运算、原生扩展加载及一个 CUDA 光栅化内核、Blender CPU/CUDA/EEVEE 试渲染、Codex 自带沙箱真实命令写入。EEVEE 软件渲染会与 NVIDIA 渲染分开记录。

仍需分别确认：Codex 模型实际执行/文件编辑、图像生成 API、模型加载推理、room_002 真实场景完整流程。仅有 Codex 登录，不能替代 OpenAI/Gemini 图像生成 API。

Dockerfile 中设置 `NVIDIA_DRIVER_CAPABILITIES=compute,utility,graphics` 仅表示请求运行时注入相关驱动组件，最终由学校平台决定。没有 NVIDIA EGL/GLX 驱动时，镜像中的 Mesa 不能保证 EEVEE 使用 NVIDIA GPU。GPU 选择交给学校分配，脚本不修改 `CUDA_VISIBLE_DEVICES`。

之前的 Codex 沙箱挂载拒绝属于运行时权限问题，换镜像不保证解决。镜像保留现有权限配置，不内置禁用沙箱的回退。若再次失败，返回包会记录真实错误，其他独立检查继续完成。

## 文件与依据

单独 Dockerfile 内嵌 gzip/base64 脚本是为了适配“只上传 Dockerfile”的平台；载荷 SHA256 在构建中验证。源码包的 `payload/` 是相同脚本的可读副本，可对照 `manifest.json`。tar/gzip 时间统一为 0，不再出现压缩包时间位于未来的警告。
