# 独立 Ubuntu 构建机

目标：在 `huang@192.168.3.66` 上实际构建并导出可供学校平台导入的 Docker 镜像。

工作目录 `/home/huang/room-image-build`：代码在 `scripts/`，日志、测试结果和镜像归档在 `return_output/`。不修改已有业务容器或清理其他镜像。

使用 v0.1.3 配方，构建时覆盖基础镜像为经过摘要校验的 NVIDIA CUDA 12.4.1 cuDNN devel / Ubuntu 22.04 / amd64。最终标签为 `room-litereality-agent:0.1.3-cuda124-r3`。它与学校内网基础镜像构建的版本不同；`base-manifest.json`、`base-image.txt`、Dockerfile SHA256 和 `image-inspect.json` 记录实际来源。

首次实际构建发现 Ubuntu 官方软件源下载缓慢并重试。对同一索引实测：官方源 30 秒仅下载约 1.6 MB，清华镜像约 6 秒完整下载约 6.5 MB。`make_remote_dockerfile.py` 因此生成 `remote-build/Dockerfile`，仅将 Ubuntu 源切换为 HTTPS 清华镜像并为索引更新设置重试和超时；APT 签名校验保留。原学校单文件配方不变，`remote-build/provenance.json` 记录差异和哈希。

GPU 大包下载过程中又观察到多次重试，而独立 curl 下载成功。参考 uv 官方问题记录 https://github.com/astral-sh/uv/issues/18735，远程配方将该层的 `UV_CONCURRENT_DOWNLOADS` 降到 2，并使用 BuildKit cache mount 缓存已完成的包。该缓存不进入最终镜像，安装使用复制模式，固定版本和 SHA256 校验不变；原重试日志保留在 `build-gpu-download-retries.log`。

三个 NVIDIA wheel（cuDNN、cuBLAS、cuFFT）先从 PyPI 官方站下载，并逐个核对 PyPI、PyTorch 官方索引与已有依赖锁文件中的 SHA256 一致。构建通过只读 named context 使用这些文件，uv 安装仍要求哈希，完成后恢复原依赖锁文件。来源记录保存在 `gpu-wheel-sources.json`，缓存目录不进入镜像。OpenCV 和 SciPy 同样预下载，并核对原依赖锁中的 SHA256，来源单独记录在 `extra-receipt.json`。cuDNN 若单连接过慢，可先运行 `fetch_cudnn_ranges.py`：4 路并发、每段 8 MiB，验证 HTTP 206 和段长度，合并后核对完整 SHA256；再运行 `prepare_gpu_wheels.py` 生成来源记录。OpenCV 可用同一脚本的 `--package opencv` 参数分段下载。

实际网络还导致后续包下载停滞，因此 `prepare_remaining_gpu_wheels.py` 根据本次构建缓存记录，集中预下载尚未缓存的依赖，并按 Python 3.10 / Linux x86_64 wheel 标签选择文件、核对原锁文件 SHA256。GPU Python 安装层开启 `UV_OFFLINE=1`：全部依赖从校验后的 wheel 或 BuildKit 缓存安装。此缓存只加速本次构建，原版本与哈希要求不变。

## 网络

2026-10-31 检查发现 Ubuntu 现有网络代理访问 Docker Hub、GitHub、PyPI 超时。Mac 同样地址访问正常。临时使用 SSH 反向转发，仅监听 Ubuntu 的 `127.0.0.1:17897`，连接 Mac 已有的 `127.0.0.1:7897` 代理。

在 Mac 保持这个命令运行，直到所有构建下载完成：

```bash
ssh -o ExitOnForwardFailure=yes -o ServerAliveInterval=20 -N \
  -R 127.0.0.1:17897:127.0.0.1:7897 huang@192.168.3.66
```

不关闭 TLS 验证，不修改 Docker daemon 的代理设置，不重启 Docker。构建 RUN 使用 host 网络访问回环代理；只给此次构建传入代理参数，不写入镜像 ENV。最终验收容器使用 `--network=none`。

## 构建与导出

完整准备和构建入口为 `bash scripts/run_remote_build.sh`，需要先建立上述 SSH 代理转发。入口包含基础镜像验证、分段预下载、哈希校验、构建、验收和导出；下面列出各阶段供故障恢复使用。

在 Mac 执行 `python3 scripts/litereality-image/make_remote_dockerfile.py`。将生成的 `remote-build/Dockerfile`、`.dockerignore`、`provenance.json`，以及 `prepare_remote_base.sh`、`build_remote.sh`、`smoke_image.sh`、`prepare_gpu_wheels.py`、`prepare_extra_gpu_wheels.py`、`prepare_remaining_gpu_wheels.py`、`fetch_cudnn_ranges.py`、`download_artifacts.py` 和 `gpu-requirements.lock` 放在远端 `scripts/` 后，在 Ubuntu 执行：

```bash
bash /home/huang/room-image-build/scripts/prepare_remote_base.sh
HTTPS_PROXY=http://127.0.0.1:17897 HTTP_PROXY=http://127.0.0.1:17897 \
  python3 /home/huang/room-image-build/scripts/prepare_gpu_wheels.py
HTTPS_PROXY=http://127.0.0.1:17897 HTTP_PROXY=http://127.0.0.1:17897 \
  python3 /home/huang/room-image-build/scripts/prepare_extra_gpu_wheels.py
HTTPS_PROXY=http://127.0.0.1:17897 HTTP_PROXY=http://127.0.0.1:17897 \
  python3 /home/huang/room-image-build/scripts/prepare_remaining_gpu_wheels.py
bash /home/huang/room-image-build/scripts/build_remote.sh
```

脚本依次验证网络、实际构建、离线 CPU 验收、默认启动 SSH 登录和重启验收、检查镜像配置、`docker save | gzip -1n` 导出并生成 SHA256。只有完整通过才写 `stage=complete`。

输出路径：

```text
/home/huang/room-image-build/return_output/build.log
/home/huang/room-image-build/return_output/build.status
/home/huang/room-image-build/return_output/cpu-smoke/
/home/huang/room-image-build/return_output/image-inspect.json
/home/huang/room-image-build/return_output/room-litereality-agent-0.1.3-cuda124-r3.docker.tar.gz
/home/huang/room-image-build/return_output/room-litereality-agent-0.1.3-cuda124-r3.docker.tar.gz.sha256
```

CPU 验收覆盖 Python 导入和依赖一致性、CUDA 扩展文件存在、CLI 版本、终端配置、Blender CPU 渲染以及 `.blend`/GLB 导出。它不代表学校 GPU 内核、模型推理、Codex 登录及命令执行或完整真实场景已验证。构建机 GTX 1070 8 GB 不是目标硬件，仍为学校 A100/3090/4090 编译。

镜像不包含账号凭据、扫描数据、模型权重。导入学校并分配 GPU 后仍需要 `room-check` 与真实场景验收。

## 构建机 GPU 实测限制

GTX 1070 / 驱动 535.309.01 上，默认容器的 ldconfig 优先选择 CUDA 12.4 compat/libcuda，触发 CUDA 804。对照测试仅将该测试容器的 `LD_LIBRARY_PATH` 加入 `/usr/lib/x86_64-linux-gnu`，选择实际注入的宿主驱动后，PyTorch CUDA 张量运算、13 项模块/扩展导入和 TRELLIS pipeline 导入通过。镜像默认 ENV 未改。

复现该测试：`ROOM_GPU_USE_HOST_DRIVER=1 bash scripts/run_gpu_smoke.sh`。原始失败与对照成功报告均保留。它不证明学校目标 GPU 的扩展内核或真实模型推理通过；不要将此旧显卡的对照设置无条件套用到学校。NVIDIA 文档说明了[前向兼容的硬件范围及错误 804](https://docs.nvidia.com/deploy/cuda-compatibility/forward-compatibility.html)和[小版本兼容中的 PTX 限制](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)。

## r2 的 Codex 验证

实际沙箱探测发现 r1 的独立 Codex 二进制缺少 bubblewrap，r2 已通过 Ubuntu 软件包补齐，并加入离线验收。复测不再报缺少程序，而是在项目目录和 `/tmp` 都报 `bwrap: No permissions to create new namespace`，测试代码未开始执行、未写出目标文件，模型调用次数为 0。观察到容器使用 `docker-default (enforce)`、Seccomp 2；本次未进一步定位到其中某一个具体规则。

因此只能确认软件依赖、CPU 渲染和指定驱动配置下的 GPU 导入通过，不能宣称 Codex 沙箱写文件或完整 Agent 流程通过。镜像安装包本身无法授予宿主机拒绝的 namespace 权限。使用 `bash scripts/run_codex_sandbox_smoke.sh` 可独立复测；保留原始日志，不修改宿主机隔离策略。

## r3 的 SSH 自动启动

默认 CMD 从 `sleep infinity` 改为 `/usr/local/bin/room-sshd`。保留 tini 和已有环境初始化入口、运行时 host key 生成、公钥认证与自定义 `ROOM_SSH_PORT`。不内置任何登录公钥或密码。

`python3 scripts/check_image_ssh.py` 使用临时密钥和两个测试容器，**不覆盖镜像启动命令**，验证默认启动、实际登录、错误密钥拒绝、PTY/tmux、SFTP、重启及自定义端口；清理测试容器和私钥，日志与诊断包写入 `return_output/`。此项通过后才导出镜像。

学校平台需要映射容器 SSH 端口并注入用户公钥。若平台覆盖 CMD，需设为 `/usr/local/bin/room-sshd`。导入后 SSH 成功不代表 Codex 的 namespace 限制已解决。
